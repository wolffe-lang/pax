Prediction: Linux forces PEEK/POKE through read-only and PROT_NONE
private mappings (copy on write) but not through a shared one's file;
a short pread/pwrite at a mapping end returns the bytes reached and a
hole at the start gives -EIO (5). PAX's position is unknown; the
transcript is the reference wherever the two disagree.

Measured on Linux (78369437's binaries; a fresh container per take; 3

uid 1000): END linux-memory-0 exit=0 takes=3, END linux-memory-1000
exit=0 takes=3. Reference: tests/mpx5-trace.d/memory.linux.
Disagreements with the prediction, recorded not hidden:
  - PEEK and POKE reach a PROT_NONE page (the poke took, mem.none.after
    0x77), and so does /proc/<pid>/mem, which also pwrites it.
  - A word straddling the end of a mapping fails -EIO (-5) for PEEK, and
    for POKE the bytes below the mapping's end are still written before
    the failure (mem.edge.pread shows 3c then seven zero bytes).
  - A kernel address and a negative offset through /proc/<pid>/mem are
    -EINVAL (-22), and PEEK of a kernel or non-canonical address -EIO.
  - After the target's exec, a descriptor opened before it reads 0 and
    writes 0; a fresh open reads -EIO at the old address.

Corrections and limits for the sig note above.
- My first report of this diff was wrong. I read the session pair that the
  suite's U1 builds for its sender rows (the .cmp and .want files, whose
  three set-ID kill rows U1 already tolerates against the Linux recording),
  not the comparison against tests/mpx5-users.d/sig.pax that failed. The
  checker prints that failure cut at 400 characters starting at line 114, and
  I did not open the full session against sig.pax until the second look, which
  is where the mem column showed.
- Yama. PAX applies ptrace(2)'s access-mode checks without Yama: same-uid
  processes may trace and read each other's /proc/<pid>/mem, as Linux does at
  ptrace_scope 0. That is security-relevant (a uid-1000 process can read and
  write the memory of any other uid-1000 process). Adding Yama
  (ptrace_scope 1: only descendants) is a later item, not this lane's.
- "Linux at scope 0 answers -5" was read from ptrace(2)'s Yama section, not
  measured: the rules forbid changing a host's setting, and the host's scope
  is 1. What was measured: a descendant's mem on Linux at scope 1 (memory
  witness, -5 for a read at address 0) and the recording's -13 for a
  non-descendant.
- final2's mpx5-users stage ran with sig.pax copied into build-fbda0bb9 while
  the job ran: dev evidence, not a run at fbda0bb9 or 884ba058.
