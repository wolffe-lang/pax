px89 — black-box measurements (no source read: QEMU, dnsmasq and Linux run as programs)

1. QEMU 8.2.2's user-mode DHCP server (hasu, localhost/px89-dhcp:1, 2026-11-03 23:18Z;
   the probe notes/px89/rig/probes/slirp-dhcp.{sh,py}: QEMU's user netdev and a socket
   netdev on one hub, no machine; the script is the client at the socket's end).
   - every answer: dst ff:ff:ff:ff:ff:ff, 10.0.2.2 -> 255.255.255.255, src MAC
     52:55:0a:00:02:02, UDP 67->68, 590-byte frames; the same with and without the
     BROADCAST flag.
   - OFFER: yiaddr 10.0.2.15, siaddr 10.0.2.2, flags 0, options 53=2, 54=10.0.2.2,
     1=255.255.255.0, 3=10.0.2.2, 6=10.0.2.3, 51=86400; no 58, 59 or 28.
   - ACK (53=5), same options, to: REQUEST in SELECTING form (50+54, from 0.0.0.0,
     broadcast), in RENEWING form (ciaddr, unicast to 10.0.2.2), in REBINDING form
     (ciaddr, broadcast).
   - NAK (53=6) to a REQUEST for 10.0.2.99 (not offered): yiaddr 255.255.255.255,
     option 56 "requested address not available".
2. dnsmasq 2.91 (Ubuntu 24.04's dnsmasq-base 2.91-0ubuntu0.24.04.2) on a tap in the
   container's own network namespace (notes/px89/rig/probes/tap-dnsmasq.sh; rootless
   podman with /dev/net/tun and CAP_NET_ADMIN makes the tap; nothing of hasu's network
   is touched).
   - a range's lease time under 2 minutes is raised to 2 minutes (30s -> "lease time 2m").
   - unasked, it sends 58 (T1) = 1m and 59 (T2) = 1m45s with a 2m lease; with
     --dhcp-option=option:T1,10 and option:T2,20 it sends 10 s and 20 s.
   - it also sends 28 (broadcast address); 6 as given (two servers, 8 bytes).
   - before its first OFFER for an address it sends an ICMP echo to that address and
     ARP requests for it: the first OFFER comes about 3 s after the first DISCOVER.
   - BROADCAST flag set: the answer is broadcast ("broadcast response" in its log);
     clear: unicast to yiaddr at chaddr.

5. QEMU 8.2.2's `-device igb` (8086:10c9), measured from PAX's own boots (kernel/gbe's
   read-backs on the serial log; hasu block B, KVM, 2026-11-04 00:30-00:50Z; the boots
   i1, i2, i3 and p3 in notes/px89-the-wire-on-metal.md; p3 ran a lane-only probe
   commit, f4eef2ca on the branch px89-probe, never merged):
   - after CTRL.RST and CTRL.SLU, STATUS.LU stays 0 for the full 10 s (STATUS
     80080481); PHY register 0 (PCTRL) reads 1140 (auto-negotiation enabled, full
     duplex, 1000) and register 1 (PSTATUS) 794d (link down, negotiation not complete)
     at MDIO address 1. Writing PCTRL with bit 9 (restart) set brings the link up in
     about 0.5 s (STATUS 80080483, PSTATUS 796d; CTRL gains RFCE and TFCE, 18100241).
   - with the link up, frames are received into the ring (RDH moves: 4 after four
     OFFERs) but ICR never shows RXDW and no INTx comes with IMS = d4: IMS reads 0
     after any write (d4, then 4); ICS = 4 sets nothing ICR or EICR reads back.
   - EIMS keeps bit 0 of 80000001 (bit 31 is dropped); IVAR0 keeps 8181; with IVAR0
     8181 (receive and transmit queue 0 to EICR bit 1) EICR reads 2 at the end of the
     run. GPIE, IAM, EIAC and EIAM read 0.
   - polled (no interrupt, `netpoll`): the DHCP lease in 0.05 s, every U0-U9 row of
     tests/mpx4-udp's user way passes, at one datagram per 10 ms tick (100 a second).
   - p4 (a second probe commit on px89-probe, daa2643b): with IVAR0 80 (receive queue 0
     to EICR bit 0) and EIMS bit 0 set, EICR reads 1 at the end of the run (the cause is
     there, unmasked) but PCI status bit 3 (Interrupt Status) stays clear (status 0010,
     command 0107: INTx not disabled), before and after EICS = 1; IMS = ffffffff reads
     back 0; ICS = 4 sets nothing, with GPIE.NSICR 0 or 1. QEMU's igb raises no INTx
     here; its MSI capability is at 50 and MSI-X at 70.
   - b8ee5892 (MSI, i5): the 82576's MSI enabled (control 0181: enabled, 64-bit, per-vector
     masking, the mask clear), EIMS bit 0 and IVAR0 80 as above: the four OFFERs land in
     the ring and no interrupt arrives (net: 0 interrupts). p5 (9fbd3ccf, six variants of
     GPIE, EIMS, EIAC, EIAM, ICS and EICS) ran with IF clear (rflags 93/97/46), so it
     says nothing about delivery; it is kept for its read-backs only (GPIE keeps 10,
     80000010 and 40000011).
   - cc28ec6b (MSI-X, i6): GPIE 80000010 (Multiple_MSIX, PBA support), IVAR0 80, MSI-X
     table entry 0 in BAR3 (a message of vector 83 to APIC 0, unmasked), EIMS bit 0: the
     interrupt comes, and DISCOVER OFFER REQUEST ACK bound in 0.04 s (D1-D3, D10 PASS).
