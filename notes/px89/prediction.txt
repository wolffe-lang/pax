px89 — the wire on metal: the prediction, written before the first change
(2026-11-03 23:25Z, base trunk b38643a5)

Black-box facts read before this was written (notes/px89/blackbox.txt):
QEMU 8.2.2's user-mode DHCP server answers every message broadcast
(ff:ff:ff:ff:ff:ff, 255.255.255.255, from 10.0.2.2) whatever the BROADCAST
flag says, offers 10.0.2.15 with options 54, 1, 3, 6 and 51 (86400 s) and
no 58 or 59, ACKs a REQUEST in SELECTING, RENEWING and REBINDING form, and
NAKs (yiaddr 255.255.255.255, option 56) a REQUEST for an address it did
not offer. dnsmasq 2.91 never leases for under 2 minutes (30s is raised to
2m), takes option:T1 and option:T2 as given (10 s and 20 s under a 2 m
lease), probes an address with an ICMP echo before it offers it (the first
OFFER comes about 3 s after the first DISCOVER), and answers broadcast when
the flag is set and unicast to yiaddr when it is not. kasumi's cabled port
is the I225-V, PCI 70:00.0, 8086:15f3 rev 03, BAR0 1 MiB (32-bit), link up
at 1000 Mb/s, DHCP from 192.168.0.1 on 192.168.0.0/24 under CachyOS; the
other port is an Aquantia AQC113CS (1d6a:94c0), down.

Intel's public I225/I226 datasheet (596659 rev 2.6) carries no register
map, no descriptor layout and no reset, PHY or interrupt programming; the
register-level manual is Intel Confidential. The 82576 (QEMU's igb) and
the I210 public datasheets agree word for word on everything the ring
driver needs. This decides R-px89-1's shape (below).

## What changes, and what each change shows

1. kernel/dhcp (new): an RFC 2131 client in the kernel, a thread of its
   own (pax_dhcpd), started only when the image's /etc/pax-net says
   `dhcp`. Predicted: DISCOVER -> OFFER -> REQUEST -> ACK against QEMU's
   server in under 0.1 s of guest time under KVM (one round each);
   10.0.2.15/24 via 10.0.2.2, /etc/resolv.conf `nameserver 10.0.2.3`.
   Retransmission at 4, 8, 16, 32, 64 s (each +-1 s, RFC 2131 4.1), the
   xid kept, `secs` counting up. T1 renew (unicast to the server), T2
   rebind (broadcast), expiry (the address, the route and resolv.conf's
   servers withdrawn, back to INIT), NAK (the same, at once).
2. kernel/ip: `configure` (the triple changed at run time; 0.0.0.0 while
   no lease is held), kernel/arp follows it. No existing row moves: the
   fixed 10.0.2.15 stays the default and is what every kernel uses when no
   /etc/pax-net names dhcp.
3. kernel/netd: UDP from port 67 to port 68 goes to kernel/dhcp when it
   runs, before kernel/udp; kernel/udp's counters never see DHCP.
4. kmain_sockets and kmain_session read /etc/pax-net from the tree; with
   `dhcp` they start the client, wait up to 30 s for a lease (printing
   one line either way) and only then run the list. kmain_sockets' and
   kmain_session's loopback lines print the address the station holds
   (10.0.2.15 for every existing row: the same bytes).
5. kernel/gbe (new): Intel's gigabit controllers on the 82576/I210
   programming model, QEMU's igb (8086:10c9, the 82576's id) and the
   I225 (8086:15f3 I225-V, 15f2 -LM, 0d9f -IT, 5502 -LMvP; the I226's
   125b, 125c, 125d: the public datasheet's table; 15fd and 125f, an
   empty flash, are refused by name). One RX and one TX ring of 64 16-byte
   descriptors (one frame each), 64 2048-byte buffers each way: 66
   frames, the same as virtio-net's, so U3/T3's `net frames 66` holds on
   igb unchanged. Advanced one-buffer receive descriptors, legacy
   transmit descriptors. INTx on the firmware's line when it is one the
   8259 can take (QEMU: 10 or 11), polled every tick by the network's
   clock when it is not (kasumi: predicted 255, as its xHCI's was).
   kernel/net keeps virtio-net's lines byte for byte and dispatches its
   frame interface to whichever device it found; virtio first.
6. The I225-only paths, named in the code and the note: the device ids,
   the reset's wait (CTRL.RST, then RAH0.AV), the link wait with no PHY
   register touched (STATUS.LU, up to 10 s), the speed's reading (the
   I210's table plus "2500?" for the value the I210 has no meaning for),
   and the register dump the metal leg logs.

## Numbers predicted

- kernel/dhcp ~900 lines of wolf, kernel/gbe ~650, net/netd/ip/arp
  changes ~150, kmain changes ~60.
- igb throughput under KVM within a factor of 2 of virtio-net's in the
  soak rows (U8: ~20,000 datagrams a second each way).
- Each dnsmasq row under KVM: 30 s (renew), 40 s (rebind), 150 s
  (expiry), 40 s (NAK), 60 s (backoff).
- CI: two new jobs (mpx4-dhcp, mpx4-igb): `Footprint: cross-cutting`.

## What is not attempted (said now so the note can be scored)

No DNS resolver (wolf-lang#831), no DHCPDECLINE after an ARP probe (the
probe is not made; named), no DHCPRELEASE at halt, no option overload
beyond reading `file`/`sname` when option 52 says so, no MSI or MSI-X for
gbe, no PHY register access, no checksum or segmentation offload, one
queue each way, one interface. No metal run: the stick is staged, the
maintainer runs it.
