# px127 probes: a program built on PAX cannot dial a host name

Both probes ran before notes/px127-names.md's prediction was written; they found the cause.

## Probe 1: the image's compiler on Linux, the program under strace (black box)

The dev image 65d972ac's own /usr/bin/wolf (0.2.39), ld.lld and /usr/lib/wolf-musl, run in the image's
root on Linux (an overlay), built the contract's probe and an argv dialer (the probe's try() over
env_args()), with the default ld.lld link and with WOLF_LD=cc: both link the same musl libc.a. Each
binary is static (no PT_INTERP). In a bare chroot holding only the program and /etc/resolv.conf
(nameserver 127.0.0.1, tools/dns-fixture there, github.com -> 127.0.0.1, a listener on :443), on Linux:

## Probe 2: the image itself under QEMU (KVM, native BIOS, igb, QEMU's user network)

The image's kernel (kmain_console.elf dce9a270...) and root archive (dev.cpio 5a8cc4d4...), each digest read
twice; tools/mkimage with boot/limine-initramfs-quiet.conf gives the image's own ISO (ac0dfe60..., the
digest its build recorded). For the calls, the same two files with boot/limine-initramfs.conf (no
`quiet`, so kernel/user prints a call PAX lacks). DHCP as the image ships it, then at the console
/etc/resolv.conf names the router, 10.0.2.2, as the real machine's names its router: QEMU hands the
guest's 10.0.2.2:53 to tools/dns-fixture (github.com -> 10.0.2.2) and 10.0.2.2:443 to a listener

The listener: four connections. The dialer's 10.0.2.2:443 at 1794449768.893; den's at 1794449782.067,
146 bytes, a TLS ClientHello naming github.com (SNI); then the /etc/hosts pass's github.com and hosts.test.

Reading: the musl resolver sends its A and AAAA questions with sendto and reads the answers with
recvmsg (47). PAX answers recvmsg -ENOSYS, so no answer is ever read: the resolver asks again after
2.5 s, gives up after 5 s, and net.connect answers io. den (glibc) reads with recvfrom and resolves.
A name /etc/hosts holds is answered before any socket is made.
