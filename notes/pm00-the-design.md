## Inputs, verified

### The scope and the baseline correction

PAX's target is a rolling binary distro with a minimal base and one build recipe format; foreign C packages go through cpkg/muzzle [P02–P04]. A language module graph is not a system package database. The distro manager owns installed paths, accounts, dependency/ABI compatibility and recovery. `wolf pkg` continues owning source-module graphs, MVS, its ledger and capability audits [P03,P15]. Neither silently acquires the other's privileges.

Three corrections matter to the schedule:

1. **The kernel can journal; not every disk does.** At this base, px68 supplies ordered-data ext3 journal commit/replay. Image roots made by `tools/mkdisk --gpt --root` default to ext3; `pax-install` explicitly formats **plain ext2** through `paxext2` [P06: README 125, 193–217, 334; P08]. An application WAL cannot fix a torn ext2 directory or bitmap. M-PM2 first uses a qualified journalled QEMU root; ordinary mutation on an installed plain-ext2 root is refused. A PAX storage/installer lane must supply a journalled fresh installation or an independently gated offline migration before M-PM4 is claimed on the current metal installation. No in-place conversion is proposed as a package operation.
2. **wolf-lang#515 is CLOSED, not a current blocker.** Closed 2026-10-25 at s263/#930, `a5378e3f`; muzzle trunk `6dd9033f` has lc02 stdio over wolf 0.2.36 variadics [P16]. This removes a language blocker, not all libc work. The current hosted compiler/runtime bridge and the final all-wolf cpkg/muzzle system are different milestones.
3. **vc15 is not an HTTP client.** Its contract builds file:// and git:// protocol-v2 clone/fetch/push, not HTTP [P14]. A reusable, bounded HTTP downloader must still be specified and gated. A server/reverse proxy is not proof that such an API exists [P17].

### Hosting boundary

Proposed shape only, based on HOSTING, not an inspection of almanta: static repository files in an operator-chosen nginx path/vhost, staged by a restricted CI deploy script patterned after wolf-web's job. The operator makes DNS/vhost/path and key decisions. CI builds in clean roots, validates/assembles signed metadata, uploads immutable blobs and versioned metadata first, verifies remotely staged lengths/hashes through its restricted job, and publishes the mutable timestamp last. It never replaces an immutable digest path in place. An upload failure leaves the old timestamp usable. Keep old snapshots/blobs through their retention window.

CI signing permissions are separate from deploy permissions. The build job cannot mint a root or approve arbitrary targets. A narrowly scoped timestamp/snapshot signer may refresh already-approved targets; an offline signing step approves targets/root. The maintainer's actual key storage/automation choice needs R-pm00-7. A failed freshness refresh should stop new installs, not execute stale metadata silently. Availability, traffic privacy, censorship and denial of service are not solved by signatures over HTTP.

No lane logs into almanta, configures nginx, changes DNS/Cloudflare/tunnels, exposes hasu, or installs a signing secret. pm00 does not say an endpoint is live.

## Evidence index

### Decisions and recommended semantics

#### Package and metadata

**R-pm00-1 — archive/compression.** A: uncompressed restricted POSIX pax at M-PM1/2, gzip as the first optional codec after streaming qualification, zstd later; B: gzip immediately using den's whole-object API; C: zstd immediately; D: xz; E: a bespoke archive. **Recommend A.** It avoids a new decoder on the first critical path and avoids making a whole-buffer codec's high RSS the install architecture. No-compression ratio is 1 for the tar byte stream (headers/padding add overhead relative to file bytes); no comparative throughput number is claimed. gzip/deflate has the closest existing wolf primitive; zstd offers a stronger performance/ratio tradeoff but needs new decoder work; xz emphasizes density with more decoder-memory/latency choices. Final codec choice must be measured on binaries, source, man pages and incompressible inputs at fixed levels, with compressed bytes/input bytes, encode/decode MB/s, peak RSS and three independent runs, not a vendor ratio treated as PAX data.

The format sources are POSIX pax [F06], gzip/deflate [F03–04], zstd [F02] and XZ [F05]; historical comparison conditions and den's existing measurements are recorded in the matrix, not treated as new results [F07,P13]. Use POSIX ustar headers plus only per-entry pax `path`, `linkpath` and needed numeric-size/time extensions. No GNU extensions, global pax headers, device nodes, sockets, FIFOs, sparse maps, xattrs, ACLs or set-ID bits in v1. Unknown mandatory features reject before touching the live root. Plain ustar alone would impose short path/link limits; a private format duplicates mature framing work. The packer normalizes order, numeric owners, timestamps and padding. The reader rejects duplicate paths, absolute names, `..`, NUL/invalid schema text, integer overflow, overlapping/conflicting types, escaping symlink/hard-link targets, missing hard-link destinations and inconsistent file lists. Only regular files, directories, relative symlinks and within-package hard links are permitted; staging never follows archive-created symlinks. Bound headers, entries, total output and expansion before allocation; validate file lengths and SHA-256, modes and owners against the authenticated manifest before promotion. Verify full blob digest before parsing it into even a staging tree.

**R-pm00-2 — metadata.** A: a strict data-only subset of wolf literal syntax for package manifest, recipe and local records, with a small standalone parser and exact-byte hashes; B: repeated key=value records; C: use the compiler's general parser/evaluator. **Recommend A, never C.** Familiar nested lists/tables fit dependencies and files without inventing escaping rules for repeated keys. Reject unknown required fields, duplicate keys, executable expressions and interpolation; schema version and feature flags are explicit. The package tool does not link or execute the compiler to read an index. Keep transport trust metadata in TUF's specified JSON/canonical-signature representation rather than claiming a novel literal encoding is interoperable TUF. Package manifest bytes are immutable signed-target objects: pretty-printing them changes their hash, not their interpretation behind the verifier's back.

Each package has name, upstream version, packaging revision, architecture/ABI, licence and source/provenance references; exact blob hash/length, installed-byte/inode estimate; required/optional dependencies, versioned provides, conflicts and explicit replacements; complete file records (path/type/mode/owner/group/length/digest or link target), config-file list and declarative actions. Source/build records bind recipe/source/toolchain/container/dependency hashes, SOURCE_DATE_EPOCH and the source package needed for licence compliance. Never put signing keys, build secrets or host paths into a published build record.

#### Building and the language boundary

**R-pm00-3 — distro recipes versus D33.** A: one declarative recipe describing immutable inputs, dependency graph, environment and ordered argv build/check/package steps; scripts allowed **only as explicit, digest-pinned build inputs in an isolated builder**, never during dependency discovery, fetching or installing; B: unconfined PKGBUILD-style evaluation on the user's host; C: only language-manifest C source lists. **Recommend A as a separately ruled distro policy, not a reinterpretation of D33.** A command invoking configure/make already executes upstream build code; hiding that in an argv list is not “no scripts.” The distinction is where and when it runs. `wolf add/build` retains D33 and does not auto-run a distro recipe. cpkg invokes the explicitly chosen isolated build workflow. Reject recipes requiring graph calculation by script. B is unsafe; C cannot build ordinary foreign software and would make the distro goal fictional.

Fetch pinned sources before the build sandbox; validate hashes/signatures; network off during build/check/package, no home mounts/secrets, no privileged container, only declared tools/inputs and a writable output root. Do not use chroot alone as a hostile-code boundary. Linux containers first, PAX-native builder only after isolation/resource-limit gates exist; until then PAX self-builds are for trusted inputs, named as such. Run two clean builds in differing paths/environment/time-zone/order with normalized SOURCE_DATE_EPOCH, compare every artifact hash, and retain build-info plus structured diff on mismatch. A reproducible malicious recipe remains malicious: human recipe review and signing approval are separate gates.

#### Resolution and ownership

**R-pm00-4 — solver.** A: a deliberately small complete backtracking constraint solver over a bounded, immutable snapshot, plus a separate checker; B: greedy “latest” or MVS; C: SAT/libsolv-style full policy engine. **Recommend A for the curated base.** Enforce a single installed version per `(name, arch, ABI-slot)`; compare all required edges, virtual/versioned provides, symmetric conflicts and replacement transitions. Optional dependencies are advisory and must not enter the hard closure without an explicit user choice. `replaces` proposes a named removal with user review, not arbitrary file overwrite permission. Select deterministic latest compatible candidates within the chosen snapshot, keep explicit holds visible, and fail with an explanation when a full solution is absent or the search budget is exceeded—never return a partial greedy plan. A SAT solver remains the measured scale-up option, not a requirement for a few dozen curated packages. Cross-check small generated graphs against exhaustive enumeration; report search-budget refusals separately from unsatisfiable proofs.

Version v1 is **epoch:upstream-release**: nonnegative decimal epoch (omitted means 0); nonempty upstream restricted to ASCII letters/digits plus `.`, `_`, `+`, `~`; positive integer package release. Compare epoch, then upstream tokens, then release. Tokenize maximal digit runs, maximal letter runs and individual punctuation; order token classes `~ < end < separator < letters < digits`. Separators compare ASCII (`+ < . < _`); letter runs compare case-sensitive ASCII lexicographically; digit runs strip leading zeroes and compare length then bytes, with all-zero runs equal. Numeric comparisons never parse into a bounded integer. Thus `1~rc < 1 < 1.0`, `1.0` equals `1.00` at the upstream level, and an epoch increase dominates all upstream changes. Reject comparator-equal duplicate versions for a name/slot in one snapshot. This is a new, versioned distro policy, **not Arch/RPM/Debian compatibility**; pm01 freezes this token-order proposal with golden/property vectors before publication. Upstream version strings requiring other semantics need an explicit recipe mapping plus provenance, not a guessed semver conversion. Epoch and release handle upstream resets and recipe rebuilds. No existing package namespace is imported implicitly.

**R-pm00-5 — rolling upgrades/multiple versions.** A: whole-snapshot-compatible transactions, one active version per slot, side-by-side only through explicit distinct slot/path packages; B: arbitrary partial upgrades; C: a full Nix-style store/profile system. **Recommend A.** Refresh and upgrade are one planned operation: do not offer “refresh indexes then install one stale closure” as a supported state. Installed unchanged packages participate in the compatibility check; a hold that prevents a consistent upgrade produces an explanation. ABI dependencies use explicit versioned capabilities, not optimistic filename inference. Keep previous package blobs and manifests for recovery, which is not installing two active versions into `/usr` simultaneously. Separate kernel/boot artifacts require a later bootable-generation gate; v1 excludes bootloader/ESP and running-kernel replacement.

Ownership index maps each installed path to package and expected type/digest. Reject collisions with another owner or an unowned existing non-directory; do not offer default `--overwrite`. Shared directories may co-own only compatible metadata. Replacements explicitly transfer declared files in the plan and keep inverse operations. Reject cross-mount payloads and mutable user data paths; `/home`, `/var` application databases and `/run` are not package payload rollback domains. Adopt pre-existing image files only through a separately reviewed bootstrap inventory whose hashes match exactly, never “everything under /bin belongs to the base.”

#### Local database, install and recovery

**R-pm00-6 — transaction model.** A: single-writer durable undo/redo log plus immutable database generations, recovery in maintenance mode on a qualified journalled root; B: live in-place edits with a final installed-db update; C: full filesystem generations/snapshots. **Recommend A**, with an explicit plain-ext2 refusal. It is crash-recoverable and serializable for the package manager, not a claim that every running reader sees an atomic tree. C is attractive later but not supported by today's filesystem/boot contract.

Proposed root-owned state: `/var/lib/<name>/` contains a permanent lock inode, `objects/sha256/` or a separately configured root-only cache, immutable `generations/<id>/` (installed packages, owners, explicit reasons, config baselines, snapshot identity), `transactions/<id>/`, and a tiny `current` record selecting a generation. Separate `trust/` monotonic metadata survives package rollback. The placeholder is not a registered name. Plain bounded records plus checksums, not SQLite until a qualified library exists. Derived indexes can be rebuilt from immutable manifests; malformed authority records stop recovery.

Transaction phases, each an idempotent state transition:

1. **Lock and recover.** Acquire exclusive flock on the persistent inode. Open root/state by descriptors, reject unsupported/mixed filesystems, active unrecovered transaction, mismatched filesystem identity, insufficient blocks/inodes or inadequate backup space. A read-only query can report a recovery-needed state but not a fictitious committed inventory. Enter maintenance mode **before** taking config baselines, backups or any live-tree plan: a lock alone cannot prevent an administrator/service changing files between backup and replacement. Downloads may be prefetched earlier, but revalidate the full plan and observed path identities under this quiescence. Verify actual journal support; statfs's ext2-family magic alone cannot distinguish ext2 from ext3. pm05/PAX must expose or safely validate an unambiguous journal-capability signal before enabling writes.
2. **Plan and verify.** Authenticate one metadata snapshot, resolve complete installed+requested state, download hash/length-bound objects, verify full digests, parse and validate them in an unprivileged staging worker. Generate a complete path/action plan and prospective database generation. Same-root-filesystem staging is required for final renames. Reject ancestor symlink races, cross-mount operations and unsupported types. No live path changes yet.
3. **Prepare durable recovery.** Write durable backup **copies** of every old regular file, symlink text and metadata; hard links in the live tree are not immutable backups if another writer can modify them. Save old config and path-presence states. Preserve hard-link topology in the recovery inventory. fsync backup files, then each newly created directory up to the already-durable transaction parent. Persist length/checksum-framed intent with old/new identities, ordered operations and plan hash; fsync it and its parent. Reserve capacity for the inverse path before any destructive action. An allocation/I/O error here leaves the old generation active.
4. **Apply while still quiescent.** Remain in maintenance/recovery boot for initial system upgrades; normal services/users do not run through a mixed `/usr`. A manager lock alone cannot stop them. A trusted rescue copy of manager+dependencies lives outside replaced paths. For each path, record durable intent before action, write a same-directory temporary inode with final content/owner/mode, sync it, rename it over the destination, sync the destination directory and record completion. For moves across directories sync both. Deletes have durable preimages and unlink+parent sync; directories removed deepest-first, created shallowest-first. Symlink installation is a name operation with parent sync; no traversal through the new link. Never truncate a live executable in place. Hard-link entries are recreated only to verified in-root destinations. Recovery examines actual inode/type/hash, not just the possibly missing completion marker.
5. **Publish committed state.** Validate the complete installed tree against the plan, sync the prospective generation (files and directories), then write+sync a new `current` temporary record and rename it, syncing its directory. `current` carrying the new generation/transaction ID is the commit decision. An auxiliary COMMITTED log record is helpful but not a second contradictory authority. Recovery after a cut at rename+directory-sync sees either old or new valid authority: old selects undo, new selects idempotent finish/verification. Keep all required preimages until this decision is durable.
6. **Finish or recover.** Before the commit decision, roll back completed/partly completed actions in reverse, recreating via temporary inode+rename and barriers; after it, finish derived caches/declarative actions or enter a named degraded/recovery state. Every recovery step itself tolerates another crash. A missing/mismatched preimage, checksum error, EIO or ambiguous generation stops in rescue, never marks success. Retain last known-good generation and blobs until explicitly collected. Orphan staged objects are garbage only when no transaction/generation references them.

Package rollback is a **new checked transaction** using saved old packages and config decisions, not rewinding trust metadata or pretending a mutable application database ran backwards. A rollback crossing a forbidden ABI or dropping a required package is refused. An intentional software downgrade is explicit and logged; it does not lower repository freshness counters. A privileged whole-disk rollback can also rewind `trust/`: without an external monotonic anchor or newly authenticated media, this design cannot claim resistance to that attacker. Keep trust outside the package inverse log, but do not pretend a different directory on the same disk is an independent hardware counter. Never silently undo an administrator's later config edits. Process isolation and journal/device flush correctness are assumptions to test, not powers provided by the package format.

A process-kill test exercises application recovery. It is insufficient for durable claims: PAX gates must cut QEMU/block writes before/after every durable transition, including fsync failure, directory creation, rename, the current-record decision and **recovery itself**, then reboot with device cache semantics that honor FLUSH. Repeat on virtio and the intended metal bus before M-PM4. Torn journal/device writes may still need filesystem rescue; a package WAL does not repair arbitrary media corruption.

#### Trust and repository

**R-pm00-7 — trust policy.** A: Ed25519/SHA-256 with a constrained but interoperable TUF role model; B: a single permanently trusted signature key; C: TLS alone. **Recommend A.** This applies TUF 1.0.37 and the Cappos threat taxonomy [T01–02], with Ed25519 as specified by RFC8032 [F01]: fixed key/signature lengths, pure Ed25519 algorithm identifier, canonical signed JSON, specified invalid-point/scalar rejection and no ad hoc prehash substitution. Distinct authorized keys count toward thresholds; duplicate signatures do not. Use separate root, targets, snapshot and timestamp roles. Proposed small-operator ceremony: offline root threshold 2-of-3 keys on separate media, offline target approval key 1-of-1, distinct restricted online snapshot/timestamp keys 1-of-1. These are roles controlled by one person, not a claim of independent organizations. Cost is ceremony and availability; a 1-of-1 offline root is the explicitly weaker alternative if three media cannot be operated reliably. Do not put a root/target private key in ordinary build CI.

Install media contains a pinned root metadata version and keys/thresholds, authenticated through the existing image distribution trust path. A first client must not fetch its root unverified from the mirror it is about to trust. Root rotation advances one version at a time and must meet both old and new thresholds. Revocation is a signed role/key change, not deleting a key file on the server; clients that have not received it remain at risk until an authenticated update or new trusted media reaches them. If root threshold is compromised, recovery is out-of-band trust reprovisioning, not an automatic network cure.

Timestamp binds snapshot hash/length/version; snapshot binds exact targets metadata; targets bind package manifest/blob hash+length and required identity/architecture. Sign/hash the specified canonical metadata bytes. Check expiry and supported spec/algorithm before acceptance; bound metadata size/version/delegation depth and all fetches. Store highest accepted role versions and trusted update-time floor durably, scoped to repository and authorized root/key epoch; verify a full role chain before using its targets. Follow TUF's prescribed timestamp/snapshot trusted-state reset after authenticated role-key rotation, rather than an unconditional numeric high-water mark that would make recovery from a fast-forward attack impossible. Make same-version/different-hash metadata an error. Metadata expiry bounds a freeze only when a trustworthy clock exists. A mirror can always deny service; retries/mirrors do not repair trust failure.

Proposed validity windows for review: timestamp 48 hours (refresh daily), snapshot 14 days, targets 90 days, root 1 year (rotate/test well before expiry). They are operations commitments, not cryptographic constants. On machines without trusted RTC/time, do not accept unauthenticated network time as proof of freshness: require operator time confirmation/new authenticated media or enter explicitly offline recovery mode. Persisted maxima prevent rollback below previously observed state but cannot detect the first freeze forever. Returning clients may update an expired old root by the protocol's sequential rotation rules; verify final unexpired trusted state before installing. Offline `file://` repair uses a pinned previously authenticated snapshot or newly verified recovery media under an explicit warning/confirmation policy; it never silently disables checks on an online install.

**R-pm00-8 — repository/cache.** A: static immutable by-hash blobs and versioned metadata, mutable timestamp as the publication edge; B: in-place package names/index mutation; C: dynamic registry server. **Recommend A.** Example shape: `metadata/1.root.json`, `metadata/42.snapshot.json`, `metadata/42.targets.json`, `metadata/timestamp.json`, and `targets/<sha256>.<logical-target-name>`, with snapshot-referenced per-architecture indexes. This follows TUF consistent-snapshot filename rules [T01]; the local cache may separately use `objects/sha256/<hex>`. Every released root version remains downloadable for sequential rotation; root metadata is not ordinary old-snapshot garbage. Index shard filenames are hash-bound targets so the client never combines arbitrary latest files. Publisher uploads all referenced immutable objects first and timestamp last. Client retries a stale mirror as a consistent failed snapshot, never splices its index with another mirror's metadata.

Mirrors are user-local or authenticated recommendations; no metadata can add credentials or arbitrary schemes. Only file/http initially, no redirects to file/credential-bearing endpoints. Freshness checks still run after HTTP 304; ETag/Last-Modified are bandwidth hints, not signatures. `Accept-Encoding: identity` avoids transport transformation of hashed bytes. Resume only for immutable objects with exact offset/Content-Range and identity; discard or restart on a 200 where 206 was requested, changed validator, wrong length or an invalid range. Hash the **entire** completed object; a valid prefix is not a verified package. Cap bytes/retries/deadlines; cache unverified `.part` bytes separately and never execute/extract them. No delta updates in v1: add only after full-download fallback, memory bounds and reconstructed target-hash verification are gated. Keep retained snapshots usable by publishing/GC policy; HTTP 404 must not induce an unverified newer plan.

#### Configuration, hooks and removal

**R-pm00-9 — `/etc` and hooks.** A: tracked three-way configuration policy plus declarative idempotent actions; B: arbitrary privileged maintainer scripts; C: overwrite defaults or freeze all configuration forever. **Recommend A.** For each config compare old packaged digest, current local digest and new packaged digest: unchanged local installs new; unchanged upstream preserves local; both changed preserves local and writes a uniquely tracked `.pmnew` proposal (the eventual suffix follows the name ruling). A locally deleted file stays deleted unless an explicit policy says otherwise. Never overwrite an unrelated pre-existing proposal file; a proposal is itself an owned transaction output. Preserve user data and offer an explicit reviewed merge, not silent text heuristics for credentials. Removal preserves modified configuration and records it as residual; explicit purge is separate and confirms exactly what will be deleted.

Allowed actions initially: create a declared system account/group from a centrally allocated ID registry, create an owned directory with declared mode, and rebuild a named derived cache by a trusted installed tool. Dependencies and action versions are data; unsupported action means plan failure. Account allocation/passwd/group edits are in the recoverable plan, with cross-file consistency before returning from maintenance. IDs are never reused automatically and accounts with data/processes are never automatically deleted. No password or login change is implied by a package install. Do not run a recipe's postinstall, arbitrary shell, remote code or package-provided root hook. Trigger cache rebuilds are coalesced, idempotent, bounded and ordered after the durable database decision; failures are reported as pending actions, not “rollback succeeded” when side effects already escaped. Service restart/reboot is explicit and deferred until the entire generation validates.

**R-pm00-10 — removal/GC.** A: explicit versus dependency install reasons, reverse-dependency validation and a previewed orphan mark/sweep; B: recursive removal on every uninstall. **Recommend A.** Removing a required package must include its approved reverse closure or fail. Optional recommendations do not retain packages unless explicitly selected. Orphans are graph-unreachable from explicit roots, not merely leaf nodes; cycles are collected together only after preview. Uninstall removes only owned paths with expected identity, preserving modified files as residuals; empty co-owned directories disappear only when the last owner leaves. GC roots include installed/retained generations, active transaction preimages, pinned offline snapshots and explicit download pins; unverified downloads have a separate bounded cleanup policy. Reserve free space before installation and fail before mutation if backups plus payload plus journal headroom will not fit.

#### Foreign packages and sharing

**R-pm00-11 — language/distro separation.** A: share small versioned digest/format utilities and immutable blobs only behind clear domain/permission boundaries; separate resolver, ledgers, ownership and trust; B: one MVS/resolver/database for both. **Recommend A.** Source identity is not binary identity. A binary package includes arch, ABI, compiler/runtime and build-dependency identities; cpkg's outputs use exactly the same binary package schema as wolf-built outputs, with their own provenance/licence metadata. cpkg is a builder front-end over muzzle, not an exemption from verification.

`wolf.sum` remains a source-tree integrity ledger; the distro database is a resolution result and installed-state authority. The existing language spec's `b3k` keyed-blake3 log signature is **not an asymmetric public repository verifier**: distributing a MAC verification secret gives the ability to forge, so do not reuse that scheme for system trust [P15:88–94]. A transparency log can later record approved binary hashes and rebuild attestations, but does not replace TUF freshness/revocation or a trusted signer. Capabilities are useful source provenance/audit signals, not confinement of an installed native executable. Do not share writable user/root caches; a root import verifies digest, length, ownership and regular-file type into its private cache, with separate hash domains/schema tags and no hard-link alias writable by the user.
