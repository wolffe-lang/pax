A. What the tree does today (read, not measured)

- A record made with a controlling terminal is keyed `tty NR sid SID`: NR is /proc/self/stat's
  tty_nr, SID its session. A record made with none is keyed `ppid P start T sid S` (px115).
- kernel/sched never reuses a pid: take_pid is a counter from 1, never wrapped and never searched.
  So on PAX a later session can never have an earlier leader's pid, in any time. The pid reuse the
  issue describes is reachable on Linux (PAX's sudo runs there too, in the suite's Ubuntu
  container) and would be on PAX the day pids are reused; on PAX the row has to stub it.
- A pty takes the lowest free number (px111), so /dev/pts/0 comes back as soon as its pair is
  closed: that half of the issue is real on PAX.

D. The choice when the leader's start time cannot be read

- start_of answers -1 when /proc/SID/stat cannot be read (the leader gone). A key with `start -1`
  would match a later caller whose leader is also unreadable, so such a key matches nothing and is
  never written: sudo asks, and remembers nothing. Not reachable in a row: a session's leader's end
  takes the terminal from the session (px111), so a caller with a terminal always has a live or
  zombie leader whose stat reads. Predicted: no row changes because of it.
